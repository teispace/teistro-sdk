Everything a consumer calls hangs off a **context**: the settings a chart
is computed under, the locale it is described in, and the ephemeris it is
computed with. A context is built once and read many times, and its
operations are grouped into **areas**.

```js
const bs = ctx.calendar.convert(date(Calendar.Gregorian, 2015, 4, 14), Calendar.BikramSambat);
const noon = ctx.time.resolve(at(day, { hour: 12 }), ianaZone('Asia/Kathmandu'));
const sky = ctx.positions({ instants: [2451545.0], bodies: [Body.Sun] });
```

`ctx.calendar.convert` and `ctx.time.convert` are two different
operations with one good name each, which is what the areas are for: on
a flat surface one of them had to be called `convertTime`.

## The areas

| area | what it answers |
|---|---|
| `calendar` | dates in the calendars the SDK carries — Bikram Sambat, Gregorian and the rest — and the arithmetic over them: a weekday, a month's length, whether a year is leap |
| `time` | a civil time to an instant and back, with the zone metadata a stored chart keeps, the time scales, and ΔT |
| `intl` | the locale engine: a message by its typed accessor, an entity's name and its forms, transliteration between scripts, and a pack loaded at runtime |
| `keys` | a catalogue key to its id and back, for the boundary's own spellings |
| `frame` | the canonical frame, and packing one to carry it |
| `chart` | a chart founded from a birth record, and a batch of them founded in one crossing |
| `almanac` | a panchanga: the five limbs of a day and its periods, for a day or a run of them |
| `engine` | the operations your **ephemeris** brings with it, beyond the ones the SDK names — see below |

And at the root, on the context itself: `positions`, the grid an
ephemeris answers; `profile`, `settings`, `settingsHash`, what the
context resolved to; and `dispose`, which frees the native handle when
you would rather not wait for the collector.

`positions` is at the root rather than in an area of its own because an
operation whose name is its own area's name is a root operation: nobody
wants to write `sdk.positions.positions`.

## One shape, four languages

The grouping is the same in every binding, and a gate holds it that way:
each binding's parity runner prints one line per operation keyed by a
canonical `<area>.<operation>` path, and `cargo xtask check-parity`
compares the reports value for value — the same numbers **and** the same
shape. What differs is only how each language spells a name.

```js
ctx.calendar.monthLength(...)   // Node: lower camel case
```

```dart
ctx.calendar.monthLength(...)   // Dart: lower camel case
```

```python
ctx.calendar.month_length(...)  # Python: snake case
```

```rust
sdk.calendar().month_length(..) // Rust: snake case, and an area is a call
```

```c
ts_calendar_month_length(...)   /* C: the ABI beneath all four */
```

An area is a **value**, not a namespace trick: a frozen class instance in
Node, a `late final` field in Dart, a `cached_property` in Python, a
borrowing view in Rust. You can hold one — `const cal = ctx.calendar`,
`let cal = sdk.calendar();` — and pass it on.

### Rust is the one that composes rather than crosses

The other three bindings call the C ABI. Rust does not, and should not:
it is the language the SDK is written in, so a Rust consumer reaching
itself through C would write a request struct for the boundary to decode
and decode a result blob to read numbers the crates had already returned
as `JulianDay` and `Longitude`. The `teistro` crate composes those
crates directly, and the C boundary is built on **it** rather than
beside it — so a C caller and a Rust consumer get the same context
resolved the same way.

What that buys, and what it costs:

- **No `dispose`.** `Drop` is the whole of it.
- **No result blob.** An operation answers with the crates' own types.
- **`positions` answers `Completed`**, so a longitude is
  `sky.columns.at(0, 0)?.lon` rather than a decoded column.
- **A context is neither `Send` nor `Sync`** — one context per worker,
  which every binding already says and Rust's compiler enforces. The
  part that decides it is the locale engine, not the ephemeris.
- **The types are stricter in two places, not merely different.** A
  date's `resolution` is a `CalendarResolution` a `match` must cover
  where the other three hand over a string, so a resolution the SDK
  gains is a compile error rather than a surprise; and a value a day may
  not have is an `Option` the compiler will not let you ignore, where
  the others give `null` and trust you to check.
- **No `buildInfo`, and none is wanted.** Cargo resolved the versions and
  there is no ABI between your program and the SDK, so there is nothing
  to hand-shake. What is worth logging at start-up is the *provider* —
  `sdk.ephemeris()?.capabilities()` gives its identity, its coverage,
  its native frame and the operations it does natively.

And an ephemeris of your own is a **trait you implement** rather than an
object literal you hand over, which changes one thing worth knowing:
coverage is a per-cell outcome. `bodies` is checked before you are
called, but an instant outside your declared span reaches you, and you
answer it with `Cell::failed(CellStatus::OutOfRange)` — so a year-long
grid whose last day runs past your data keeps the 364 days you can
compute. The other three reach the port through an adapter shim that
refuses the whole batch instead, because a provider in those languages
answers columns and not statuses.

## `sdk.engine`

A real ephemeris does more than the SDK has ported. `engine` is where
those operations are, named for what it is: *this particular engine, not
the ephemeris port*. It answers what the engine describes about itself —
the manifest, an operation's signature — and calls one by name.

The adapter's own package carries a **typed façade** over them, which is
a value you take rather than a method the SDK promises:

```js
import teimeris from '@teistro/ephemeris-teimeris';

const engine = teimeris(ctx.engine);
engine.tmBodyName({ body: 0 });   // 'Sun'
```

That way nothing type-checks that the SDK has not installed, and the port
stays agnostic: the SDK knows an engine has operations, and the adapter
knows which.
