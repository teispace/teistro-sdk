# Documentation site

Status: `research`, 2026-09-04. Feeds Q11. Sources: 2026 comparisons of
Fumadocs, Nextra, Starlight and Docusaurus; Teimeris's generated docs model.

## Requirements

1. API reference generated from the IDL for every binding, with per-language
   tabs showing the same entry point in Node, Python, Dart, Rust and C.
2. Guides whose examples are executed by the build (Teimeris
   `doc_snippets.py`).
3. Conceptual pages: settings and profiles, the ephemeris port, localisation,
   calendars, the rule engine, each tradition's module.
4. Versioned docs per SDK version; a changelog with the "Numbers" rule.
5. Localised docs at least in English and Nepali (the product is
   Nepali-first); the site framework must support i18n routing.
6. Search, dark mode, MDX components for chart diagrams and interactive
   examples (a wasm build of the SDK running in the docs is the best demo,
   as ICU4X's Diplomat demos do).
7. Generated pages (reference, accuracy, conformance, sizes) must be
   checked in and diffed by a gate so the site is never stale while the
   tree is green.

## Candidates

| framework | fit | notes |
|---|---|---|
| Fumadocs (Next.js, RSC) | strong if the docs live in a Next.js product or need custom React UI and OpenAPI-style reference generation | the maintainer's stated preference ("Next.js with a docs library"); shadcn-style composition; i18n supported; versioning via routing conventions |
| Starlight (Astro) | strong for a standalone static site: fastest builds, built-in i18n, search, accessibility defaults | less custom-UI freedom than Next.js; React islands available |
| Nextra (Next.js) | quick content-first site | fewer reference-generation affordances than Fumadocs |
| Docusaurus | the most batteries (versioning, i18n, plugins, large community) | React 18 era stack, heavier; strong for long-lived multi-version docs |
| mdBook | Rust ecosystem standard | not enough for a multi-language product site |

## Recommendation

Fumadocs, given the maintainer's Next.js preference and the need for custom
components (chart diagrams, interactive wasm examples, per-language API
tabs). Starlight is the fallback if the site must be static-only and
build-fast with no product coupling. Either way:

- the API reference is generated by the SDK's own tool from the IDL into
  MDX, one page per entry point, with per-binding snippets;
- concept and guide pages are authored in `docs/` in this repository and
  mirrored into the site by the build, so there is one source;
- the site lives in a `site/` directory of the SDK repository (or a
  separate repository if Q14 says so) and deploys on tag.
