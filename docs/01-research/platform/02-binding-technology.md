# Binding technology

Status: `research`, 2026-09-04; the spike this page asked for ran on
2026-09-05 and decided option A (ADR-0007, `spikes/02-binding-toolchain/`):
the lean below held, and two of its risks proved decisive (Diplomat's
JavaScript and Dart backends take no callbacks, and trees marshal an order
of magnitude slower through accessors). Feeds Q2 and Q3. Sources: Diplomat
(the June 2026 design post and the repository), UniFFI's user guide, the
flutter_rust_bridge, napi-rs, wasm-bindgen and PyO3 ecosystems, Teimeris's
`tools/idl` toolchain and its Java FFM binding plan.

## The requirement

Same API, same signatures, same behaviour in every language; one source of
truth; a parity gate; callbacks from the core to consumer code (the
ephemeris port, and later custom calendars, rule packs and data providers);
batch shapes with typed arrays; no global state; packaging per ecosystem
with prebuilt binaries and a source fallback.

## Approaches

### A. C ABI plus IDL plus generators (the Teimeris way)

The core exports `extern "C"` functions with a header (generated by
`cbindgen` from Rust). Teimeris's `extract.py` parses such headers into an
IDL using parameter roles (handle, struct-in, struct-out, array with
capacity), and `gen_node.py`, `gen_wasm.py`, `gen_python.py`, `gen_rust.py`,
`gen_dart.py`, `gen_java.py` produce the mechanical layer; a thin hand-written
ergonomic layer per language is held to parity by a gate.

- Strengths: complete control of the ABI contract; one description that
  also generates the API reference and migration tables; uniform
  conventions with Teimeris so consumers learn one style; Java FFM and any
  future language get a path via the C header; callbacks are C function
  pointers with a `user_data` pointer, universal.
- Weaknesses: the generators are ours to maintain (Teimeris already
  maintains six); idiomatic output is only as good as the ergonomic layer;
  richer types (nested results, trees, enums with payloads) need a wire
  encoding across the C boundary (Teimeris used flat structs; the SDK has
  trees, so a serialised result shape such as a length-prefixed binary or
  flat columnar arrays is needed for the big results).

### B. Diplomat

A Rust bridge crate with proc-macro attributes; `diplomat-tool` generates C,
C++, JavaScript/TypeScript (with wasm), Dart and Kotlin bindings (Python via
nanobind in progress, Java in a separate repository). Opaque types are
pointers, structs are copied, traits are supported as a fourth kind of type
in some backends with callbacks; lifetimes are handled by "lifetime edges" in
GC languages; ICU4X ships its whole API this way.

- Strengths: IDL-free, idiomatic output, proven at ICU4X scale, hub-and-spoke
  (one bridge, many backends), automatic demo generation, active
  development.
- Weaknesses: no Swift backend; Python and Java not yet mature; the C ABI
  is generated rather than designed, so `struct_size` extensibility and
  Teimeris-style conventions are not the default; callback and trait
  support varies by backend (a risk for the ephemeris port in JS and Dart);
  the ergonomic layer is still ours.

### C. UniFFI plus per-ecosystem tools

UniFFI (Kotlin, Swift, Python, Ruby; foreign trait implementations
supported with `Send + Sync` and `Result` requirements), napi-rs for Node,
wasm-bindgen for wasm, flutter_rust_bridge for Dart, PyO3 for Python.

- Strengths: each tool is the best in its ecosystem; foreign traits in
  UniFFI are exactly the ephemeris-port shape for mobile.
- Weaknesses: five descriptions of one API; parity becomes a test problem
  rather than a generation property; behaviour drifts (Teimeris found this
  with two files that were 69% identical).

### D. WebAssembly component model

WASI 0.3 was ratified in June 2026 and jco transpiles components for
browsers, but the component model is not native in browsers and the
non-web ecosystems are not built on it. Not a binding strategy today; worth
watching for the wasm package's shape in v2.

## Comparison against the requirement

| requirement | A (C ABI + IDL) | B (Diplomat) | C (per-ecosystem) |
|---|---|---|---|
| one source of truth | the header | the bridge crate | none |
| parity gate | generated from the IDL | generated from the bridge | test-only |
| callbacks for the ephemeris port | C function pointers, universal | traits, backend-dependent | UniFFI foreign traits, napi ThreadsafeFunction, frb callbacks |
| batch and typed arrays | flat columnar arrays by design | slices supported | each tool supports typed arrays |
| tree-shaped results | needs a wire encoding | opaque handles with accessors, or serialisation | native objects per tool |
| ABI stability contract | designed (Teimeris `COMPATIBILITY.md`) | generated | none |
| Swift | via C header | no | UniFFI |
| Java | FFM over the header (Teimeris plan) | in development | none |
| docs generation | from the IDL | from bridge docs | per tool |
| maintenance | generators are ours | tool is external, ergonomic layer ours | five tools |

## Recommendation

Spike A and B in Phase 0 on the same slice: one context type, one settings
struct, one batch call returning a tree-shaped result, and the ephemeris
port callback implemented in JavaScript and in Dart. Measure: lines of
generated and hand-written code, callback cost per position, result
marshalling cost for a full chart, and how idiomatic the output reads.
Decide with the numbers.

The research lean is **A**, because the SDK's results are trees and grids
that need a designed wire encoding either way, because the ephemeris port
must be fulfillable from every language without depending on a backend's
trait support, and because sharing the toolchain with Teimeris gives
consumers one convention across Teispace SDKs. Diplomat's idiomatic output is
the thing to beat, and the spike will show whether the ergonomic layer in A
can match it at acceptable cost.

## Result marshalling across the C boundary

Whatever the tool, a full chart is thousands of values in nested shapes.
Three encodings are on the table, to be measured in the spike:

1. **Columnar flat arrays** for grids (positions, cusps, dasha rows), the
   Teimeris path that is within 5% of C.
2. **A compact binary format** (a Teimeris `serial.h`-style blob or a
   FlatBuffers-like layout) for whole results, decoded lazily on the
   language side.
3. **Opaque handles with accessors** for large results, so the consumer
   pulls only the fields it reads (the Diplomat default).

The likely answer is a mix: grids as columns, big results as blobs, small
results as structs.
