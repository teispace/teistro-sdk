# `teistro-serial`

Status: `built`, 2026-09-07. The design is
[`docs/03-design/serial-and-the-envelope.md`](../../docs/03-design/serial-and-the-envelope.md);
the measurement that tested it before a line of this crate existed is
[`docs/03-design/serial-measured.md`](../../docs/03-design/serial-measured.md),
generated by `cargo xtask serial` and held by `check-serial`.

One JSON document for a chart, and one way of writing it that two
bindings agree on byte for byte.

| module | what it settles |
|---|---|
| [`canonical`](src/canonical.rs) | the two forms: the fixed hash form, and the rendering that reads `output.precision` |
| [`seal`](src/seal.rs) | a value and its provenance, with the hash the constructor computes |
| [`document`](src/document.rs) | every section the chart layer produces, under one envelope |

## What the pass found

**The content hash was the hash of nothing.** `Provenance` carries every
field ADR-0020 asks for, and the one the envelope exists for — the hash
of the value — is set to `Hash::of(&[])` by `Provenance::new` as a
placeholder and was replaced by **one producer of three**. A founded
chart and a daily panchanga both went out claiming a hash of the empty
string.

That is a shape problem, not a bug in a producer: a value and its stamp
are built separately and joined at the end, so the one field that
*cannot* be filled until the value exists is the one everybody forgets.
`Sealed::new` is the only constructor and it computes the hash, so a
stale one is not representable.

**The foundation could not be serialised at all.** Every other Phase 4
value is computed from `ChartFoundation`, and it — with `Bhavas`,
`ChartDay`, `ChartZodiac`, `GrahaPosition`, `Placement` and the rest —
derived no `Serialize`. The SDK could not publish a chart. They do now.

**A number needs a stated format.** Rust's JSON layer writes `1e-6`
where JavaScript's writes `0.000001`:

| value | Rust's layer | JavaScript's |
|---|---|---|
| 10⁻⁶ | `1e-6` | `0.000001` |

Two bindings that agree about the number disagree about the bytes and
therefore about the hash. So the canonical grammar has **no exponent at
all**: a decimal, up to twelve places, trailing zeros trimmed, no `-0`.
A binding implementing that grammar needs no float printer of its own.

**The form itself is canonical**, measured over the corpus's 55
documents: keys in code-point order at every depth, the same bytes
twice, and the same bytes however the value's own maps were ordered.

## Two forms, and why they are two

- **The hash form is fixed and settings-independent.** A hash that moved
  with a display setting would be a worse cache key — a reader would
  find the same answer under two hashes and recompute.
- **The rendered form honours `output.precision`**, which names the
  decimals of an angle, an instant and a score. That knob had **no
  reader** — the third such found in as many modules, after
  `state.combustion_orbs` (registry entry 23) and
  `houses.module_overrides`.

Nothing is lost by keeping precision out of the hash: it is part of the
resolved settings, so the settings hash already tells two results apart.

## The document

Every section but the foundation is optional, because a caller that
wants a panchanga should not pay for a divisional chart. The foundation
is not, because every other section is computed from it. The whole is
sealed **once** — the provenance of all the sections is the same
provenance, and repeating it seven times would make the JSON larger than
the values.

## Tests

22: 13 beside the rules they test, 6 over a whole document, and 3 doc
examples.

- `tests/document.rs`: every Phase 4 value in one place, serialising;
  the seal carrying its own hash where the founder left a placeholder;
  the hash moving when any section does; the form a **fixed point** with
  every number written without an exponent; and the rendering reading
  the precision knob the hash form ignores.
